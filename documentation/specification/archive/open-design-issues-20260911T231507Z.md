# Direct KG — Remaining Decisions Handoff

## Purpose

This document is a handoff checklist of the Direct KG transformation topics that are **still open and require discussion or formal definition**.

It intentionally excludes rules that have already been agreed and formalized, including the established rules for:

- ordinary class-to-OWL-class transformation;
- primitive datatype recognition and XSD mapping;
- custom datatype reification;
- `void` and `propertyType = null`;
- attribute property kind, domain, range, and multiplicity basics;
- optional `only` restrictions;
- ultimate-sortal and broad cross-category disjointness;
- property identity and collision handling;
- IRI strategies, base IRI, name normalization, and source-ID escaping;
- unnamed class and relation naming;
- stereotype-derived relation naming already accepted;
- the special `material` naming rule based on its grounding relator;
- diagnostics already agreed for relation naming.

The objective is to make the remaining specification work explicit and ordered.

---

# 1. Input JSON contract and VP-plugin version compatibility

## Status

**Open. High priority.**

The Direct KG input contract is already fixed:

```text
JSON generated by ontouml-vp-plugin
```

What remains to be defined is **which VP-plugin serialization versions Direct KG supports** and how compatibility with older VP-plugin-generated `ontology.json` files is handled.

This matters because the current plugin implementation differs in some details from older catalog exports and from the separate standalone `ontouml-schema`. Direct KG should not silently expand its input scope to arbitrary standalone-schema documents.

Examples relevant to the VP-plugin contract include:

- the current plugin serializes `isExtensional`;
- the current plugin serializes `propertyAssignments`;
- the current plugin represents model associations as `Relation` elements with relation-end properties;
- historical catalog `ontology.json` files may have been generated by older VP-plugin versions and may differ in field shape or naming.

## Decisions required

Define:

1. whether Direct KG supports:
   - only JSON generated by the current supported `ontouml-vp-plugin` version;
   - or also selected older VP-plugin-generated JSON formats found in the OntoUML catalog;

2. if more than one VP-plugin serialization version is supported, whether version/dialect detection is automatic;

3. what happens when known legacy VP-plugin fields are encountered;

4. what happens with unknown fields in otherwise supported VP-plugin JSON;

5. whether an incompatible VP-plugin serialization:
   - generates an error and stops;
   - or is handled through a defined compatibility layer.

## Important principle

The Direct KG semantic specification MUST treat VP-plugin-generated JSON as the source contract. The standalone `ontouml-schema` can be used as a reference when useful, but it MUST NOT implicitly broaden the accepted input format unless that scope is explicitly changed later.

# 2. `«type»`, `«instantiation»`, higher-order modeling, and OWL punning

## Status

**Explicitly deferred and still open. Highest semantic priority.**

`«instantiation»` has deliberately been excluded from ordinary stereotype-derived property naming until the higher-order representation is settled.

## Topics that must be defined together

### 2.1 `«type»`

Determine how an OntoUML class stereotyped `«type»` is represented in OWL.

Questions include:

- Is it only an `owl:Class`?
- Is OWL 2 punning used so that the same IRI can act both as a class and an individual?
- Are different IRIs used for the type-as-class and type-as-individual?
- Is some other metamodeling strategy preferable?

### 2.2 `«instantiation»`

Determine whether an OntoUML `«instantiation»` relation becomes:

- `rdf:type`;
- an OWL object property;
- a metamodeling/punning construct;
- an annotation;
- or some combination.

Avoid mapping it to `classifiedBy`, `classifies`, `instanceOf`, or `hasInstance` until this is decided.

### 2.3 `order`

The source can represent:

```text
1
2
3
...
*
```

Determine whether and how the class's instantiation order affects generated OWL.

### 2.4 `isPowertype`

Determine whether Cardelli-powertype semantics can or should be represented in Direct KG.

### 2.5 Generalization-set `categorizer`

The current `ontouml-vp-plugin` serializes an optional generalization-set `categorizer`, representing the higher-order class associated with the specific classes of that generalization set.

This belongs to the same higher-order problem and should be handled consistently with:

- `«type»`;
- `«instantiation»`;
- punning/metamodeling;
- `order`;
- `isPowertype`.

# 3. Inverse-property policy

## Status

**Open. Highest priority.**

Direct KG currently generates a forward OWL property from an OntoUML binary relation. The policy for inverse properties is not yet defined.

## Decisions required

### 3.1 Whether inverses are generated

Possible policies:

- never;
- always;
- optional through a CLI/configuration argument.

### 3.2 Named inverse versus anonymous inverse expression

If the objective is only to preserve source-end cardinality, Direct KG may be able to use an OWL inverse property expression without necessarily minting a named inverse property.

Decide whether named inverses are required for usability or only generated on request.

### 3.3 Inverse naming precedence

A likely rule to evaluate is:

```text
forward property  ← target-end role
inverse property  ← source-end role
```

When role names are absent, determine how stereotype-derived inverse names participate.

Examples already available from the accepted stereotype registry include pairs such as:

```text
hasComponent / componentOf
hasMember / memberOf
isCharacterizedBy / characterizes
hasParticipant / participatesIn
```

### 3.4 `owl:inverseOf`

If both named directions are generated, determine whether Direct KG MUST assert:

```text
forward owl:inverseOf inverse
```

### 3.5 Collision handling

Inverse names must use the same deterministic collision framework already defined for generated properties.

### 3.6 Self-relations

Define behavior where source and target are the same class and forward/inverse base names collide.

### 3.7 Interaction with `material`

If an unnamed material relation derives its forward name from a relator, define how an automatically generated inverse would be named.

# 4. Relation-end multiplicities

## Status

**Open. High priority.**

Attribute multiplicity mapping has already been defined, but binary-relation end multiplicities require an explicit formalization.

## Decisions required

For a relation:

```text
A --p--> B
```

with multiplicities on both ends, define:

- which end constrains `A`;
- which end constrains `B`;
- how lower and upper bounds become OWL restrictions;
- how the source-side multiplicity is represented if no named inverse property is generated;
- whether anonymous `ObjectInverseOf(...)` expressions are acceptable;
- whether cardinality restrictions remain unqualified, relying on the global range, or use qualified cardinalities;
- how this interacts with optional `only` generation.

## Edge cases

Define behavior for:

- `cardinality = null`;
- `*`;
- exact cardinalities;
- finite ranges;
- theoretical/non-numeric multiplicities such as `a..b`, which the VP-plugin model can serialize even though they cannot be converted directly to numeric OWL cardinalities.

Unsupported multiplicity expressions need an explicit warning/fallback policy.

# 5. `«enumeration»`

## Status

**Open. High priority.**

Enumeration classes and their literals have not been mapped yet.

## Decisions required

Determine whether an OntoUML enumeration becomes:

### Option family A — reified class

```text
:Color a owl:Class ;
       owl:oneOf ( :Red :Green :Blue ) .
```

with enumeration literals represented as individuals.

This would imply that an attribute typed by `Color` is likely transformed into an `owl:ObjectProperty`.

### Option family B — OWL datatype/data range

Represent the values through an OWL data range, potentially using `DataOneOf`.

This would imply an `owl:DatatypeProperty`.

### Other questions

Define:

- IRI generation for enumeration literals;
- labels for literals;
- datatype of lexical enumeration values, if applicable;
- empty enumerations;
- duplicate literal names;
- generalization involving enumeration classes;
- whether enumeration literal identity is lexical or modeled-resource identity.

# 6. Generalization between relations

## Status

**Open.**

The current VP-plugin `Generalization` model explicitly supports generalizations involving two relation classifiers:

```text
relation → relation
```

The natural OWL mapping to evaluate is:

```text
specificProperty rdfs:subPropertyOf generalProperty
```

## Decisions required

Define:

- whether this mapping is adopted;
- object-property/data-property compatibility requirements;
- interaction with distinct property IRIs;
- interaction with inverse properties;
- whether relation generalization automatically carries subsetting semantics for relation ends;
- diagnostics for impossible object/data property combinations.

# 7. Generalization sets

## Status

**Open. High semantic importance.**

Generalization sets contain:

- `isDisjoint`;
- `isComplete`;
- their member generalizations;
- optional `categorizer`.

Class and relation generalization sets need to be treated separately.

## 7.1 Class generalization sets

Evaluate mappings such as:

### Disjoint

```text
owl:AllDisjointClasses
```

or equivalent pairwise disjointness.

### Complete

Represent that the general class is covered by the union of the specific classes.

### Disjoint + complete

Evaluate use of:

```text
owl:disjointUnionOf
```

when appropriate.

## 7.2 Relation generalization sets

Relations can also participate in generalization.

Potentially:

- disjoint relation specializations may use `owl:AllDisjointProperties`;
- OWL 2 does not provide an ordinary property-union constructor equivalent to class union, so a *complete* relation generalization set cannot simply be translated like a complete class generalization set.

An explicit support/limitation policy is therefore required.

## 7.3 `categorizer`

Handle together with the higher-order/punning work in section 2.

---

# 8. Property subsetting and redefinition

## Status

**Open.**

The source JSON exposes:

```text
subsettedProperties
redefinedProperties
```

for properties/relation ends.

## Subsetting

The VP-plugin input can contain both explicit `subsettedProperties` references and generalizations involving relations.

Define how these constructs relate in Direct KG, and evaluate whether subsetting should generate:

```text
rdfs:subPropertyOf
```

between the corresponding generated OWL properties.

## Redefinition

Redefinition is not necessarily identical to ordinary subproperty semantics.

Determine:

- whether it can be represented faithfully in OWL;
- whether some part maps to `rdfs:subPropertyOf`;
- whether cardinality/range restrictions must be carried separately;
- or whether redefinition should initially be ignored/preserved as annotation with a warning.

# 9. Transformation of `«derivation»` itself

## Status

**Open.**

Direct KG already uses `«derivation»` internally for one accepted purpose:

```text
unnamed «material» relation
→ grounding «relator»
→ derive material-property name from relator name
```

That does **not** define how the derivation relation itself appears in the generated KG.

## Problem

A derivation can connect:

```text
a relation classifier → a class
```

while ordinary Direct KG relations are represented as OWL properties.

This creates a metamodeling issue: the source relation being derived is not naturally an ordinary individual in the target OWL ontology.

## Decisions required

Determine whether derivation is:

- omitted after serving transformation-time purposes;
- represented through annotation;
- represented through OWL punning/metamodeling;
- reified;
- or handled by another explicit mechanism.

This should probably be discussed near the higher-order/punning work.

# 11. `isAbstract`

## Status

**Open.**

The distinction between:

```text
«abstract»
```

and:

```text
isAbstract = true
```

has already been established.

What remains is the actual target behavior.

## Questions

OWL has no direct construct meaning:

> this class/property classifier may not have direct instances/assertions except through a specialization.

Define whether Direct KG:

- ignores `isAbstract`;
- preserves it as an annotation;
- emits information/warning;
- or introduces a metamodeling encoding.

Remember that `isAbstract` applies to classifiers, so relation classifiers may also carry it.

The current `ontouml-vp-plugin` serializes `isExtensional`.

# 14. `restrictedTo`

## Status

**Partially used conceptually, but direct transformation policy remains open.**

`restrictedTo` records the possible ontological natures of a class's instances.

It has already informed Direct KG semantic reasoning, especially the broad disjointness design, but the target representation has not been formally specified.

## Decisions required

Determine whether `restrictedTo`:

- is used only internally to interpret/validate source stereotypes;
- directly generates target OWL axioms;
- is preserved as annotation;
- affects disjointness beyond the current stereotype-based shortcut;
- controls higher-order treatment when `type` is among the allowed natures.

This is particularly important for classes whose effective `restrictedTo` set is broader than the usual default associated with their stereotype.

---

# 15. `isOrdered`

## Status

**Open.**

Properties can be marked ordered.

Plain OWL object/data properties do not directly encode UML-style ordering of multiple property values.

## Decisions required

Choose whether to:

- ignore the flag;
- preserve it as annotation;
- warn when `true`;
- or introduce a list/sequence reification pattern.

For Direct KG's pragmatic goals, a lightweight annotation/diagnostic policy may be preferable to structural list reification, but this remains to be decided.

---

# 16. `isReadOnly` and existential dependence

## Status

**Open. Semantically relevant.**

The VP-plugin serializes `isReadOnly` for every property, including both class attributes and relation ends.

For **relation ends**, the plugin's relation model gives this flag additional OntoUML significance: it uses `isReadOnly` on the opposite relation end to determine whether the source or target is **existentially dependent**.

For **class attributes**, that relation-end interpretation does not apply automatically, so their `isReadOnly` treatment must be considered separately.

## Decisions required

Define:

### Relation ends

- whether existential dependence encoded through relation-end `isReadOnly` generates any OWL axiom;
- whether it is already fully captured by the corresponding OntoUML relation stereotype in the cases where such a stereotype is present;
- whether `isReadOnly` should additionally be preserved as an annotation;
- what happens when `isReadOnly = true` occurs on a relation that does not otherwise carry a stereotype from which Direct KG derives existential-dependence semantics.

### Class attributes

Determine whether attribute `isReadOnly` is:

- ignored;
- preserved as an annotation;
- or otherwise represented.

Any direct OWL mapping should be justified from the OntoUML/UFO semantics rather than inferred from UML mutability alone.

---

# 17. `aggregationKind` beyond naming/orientation

## Status

**Partially used, but not fully defined.**

`aggregationKind` is already useful for identifying the whole end of mereological relations such as `componentOf`.

What remains is whether it should generate any further OWL semantics.

## Decisions required

For:

```text
COMPOSITE
SHARED
NONE
```

decide whether Direct KG:

- uses them only during transformation;
- preserves them as annotations;
- derives any property characteristics or constraints.

Avoid assuming that UML composite/shared aggregation directly corresponds to a standard OWL property characteristic without explicit justification.

---

# 18. Additional OWL semantics from relation stereotypes

## Status

**Open.**

The accepted stereotype registry currently determines **property names**.

It does not yet define whether stereotypes also generate structural OWL axioms.

Potential questions:

- should any parthood property be transitive?
- should any be asymmetric?
- irreflexive?
- functional?
- inverse-functional?
- should characterization or mediation generate subproperties of some generic property?
- should event relations receive property characteristics?

## Recommended discussion principle

Evaluate each axiom individually from UFO/OntoUML semantics.

Do not infer OWL property characteristics merely because they sound intuitively plausible.

# 19. Generated labels for unnamed elements

## Status

**Partially defined; one target-side detail remains open.**

For unnamed classes, the existing decision is:

```text
synthetic IRI
→ no invented rdfs:label
```

For unnamed relations, Direct KG can generate semantically useful IRIs such as:

```text
hasComponent
isCharacterizedBy
enrollment
```

It has not been formally settled whether these generated names should also become `rdfs:label` values.

## Decision required

Choose between:

### Strict source-fidelity

```text
source name absent
→ no rdfs:label
```

even when a semantic IRI name was generated.

### Generated usability label

Create a label from the generated property name and clearly treat it as generated rather than source-provided.

Consistency with the already-settled unnamed-class policy should be considered.

# 20. Source-ID traceability in name-based IRI mode

## Status

**Open.**

Name-based IRIs are readable but may change when the modeler renames an element.

Direct KG already has access to stable source IDs.

## Decision required

Determine whether generated resources should preserve the original OntoUML source ID through an annotation, for example using:

This would improve:

# 21. Annotation and language-tag policy

## Status

**Open beyond the already-defined basic `rdfs:label` rule.**

The current `ontouml-vp-plugin` element model serializes multilingual:

- `name`;
- `description`.

Both are represented through the plugin's `MultilingualText` structure.

## Decisions required

Define at least:

```text
name        → rdfs:label
description → ?
```

A likely candidate for `description` is `rdfs:comment`, but this has not yet been accepted.

## Language tags

Define how the language-tagged entries in `MultilingualText` are transferred to RDF literals.

The default principle should be:

```text
explicit source language tag
→ preserve it
```

Direct KG SHOULD NOT invent or infer a language tag that is not represented by the VP-plugin JSON source.

If multiple language variants exist, determine whether all are emitted or whether any configured language-selection behavior is supported.

## Multilingual names used for generated IRIs and property names

The already-adopted `--iri-strategy name` and relation-naming rules require a single lexical source whenever a class name, relation name, role name, or relator name is used to generate an IRI local name.

Because the VP-plugin JSON can contain multiple language variants for `name`, Direct KG still needs an explicit deterministic rule for selecting that lexical source.

Define:

- which language variant is preferred when more than one name is available;
- whether this uses a configured language/preference order;
- what deterministic fallback is used when the preferred language is absent;
- whether the same selection rule MUST be used consistently for class IRIs, attribute IRIs, relation names, role-name fallbacks, relator-derived `material` names, and synthesized source-target names.

This decision is required for the existing name-based IRI strategy to be fully deterministic on multilingual VP-plugin input.

# 23. Package semantics and namespaces

**Open.**

OntoUML packages organize model elements.

Direct KG currently has one configured base IRI strategy.

## Decisions required

Determine whether packages:

- are completely ignored in generated semantic structure;
- influence generated IRIs;
- become OWL ontologies/modules;

# 24. Ontology IRI and ontology header

## Status

**Previously omitted; open and important.**

A base IRI for generated entities is not necessarily the same thing as the IRI of the generated `owl:Ontology`.

For example:

```text
resource namespace:
https://example.org/directkg#
```

could correspond to ontology IRI:

```text
https://example.org/directkg
```

but this has not been defined.

## Decisions required

Define:

- whether an `owl:Ontology` declaration is always generated;
- ontology IRI;
- relationship between ontology IRI and `--base-iri`;
- version IRI policy, if any;
- imports;
- ontology label/title/description;
- provenance metadata;
- whether source project metadata is propagated.

Direct KG is intentionally not a gUFO-based transformation, so no gUFO import should be introduced accidentally.

# 25. Diagrams, element views, and layout geometry

## Status

**Open as an explicit scope policy.**

The current `ontouml-vp-plugin` project JSON can contain diagrams and diagram-element views used to describe concrete visual presentations of the model.

These presentation structures should not accidentally affect the generated domain semantics.

## Decisions required

Define whether Direct KG:

- ignores diagrams and element-view/layout information silently;
- preserves selected diagram metadata as annotations;
- or exposes any diagram provenance separately from the semantic OWL output.

The default semantic expectation should be that layout, paths, coordinates, and other concrete-syntax information do not change the ontology generated from the underlying model elements.

# 26. Unknown or non-standard stereotypes

## Status

**Open.**

The serialization layer can be syntactically more permissive than the official OntoUML stereotype vocabulary.

Direct KG therefore needs an explicit policy for:

- unknown class stereotypes;
- unknown relation stereotypes;
- unknown property stereotypes.

## Decisions required

Possible behavior:

```text
unknown stereotype
→ preserve structural transformation
→ emit warning
→ do not invent stereotype semantics
```

or fail fast.

The preferred policy should be consistent with Direct KG's pragmatic approach and existing unsupported-`void` diagnostics.

# 27. Unsupported or dangling references

## Status

**Open as a general transformation policy.**

Examples:

- missing `propertyType` reference target;
- relation end referencing a missing class;
- generalization referencing an absent classifier;
- generalization set referencing a missing generalization;
- derivation referencing a missing source/target;

## Decision required

Define the global rule for malformed references:

- fail the complete transformation;
- skip the affected construct and warn;
- preserve what can safely be generated.

This is distinct from semantic validation. It concerns source graph integrity required to execute the transformation.

# 28. Output serialization/profile contract

## Status

**Open, lower semantic priority but required before implementation is complete.**

Define:

- default RDF syntax, likely Turtle;
- optional serializations, if any;
- default prefixes;
- whether output is guaranteed OWL 2 DL;
- whether some optional features may move output into OWL Full;
- deterministic ordering expectations;
- whether warnings/INFO diagnostics are emitted to stderr, log file, or structured report.

The OWL-profile question is particularly important if punning/metamodeling or reification choices are introduced.

# Corrections to the earlier remaining-items list

The previous informal list was directionally correct, but validation against the actual VP-plugin source contract requires the following corrections and additions.

## Correction 1 — the input source is already fixed

Direct KG's source is JSON generated by `ontouml-vp-plugin`.

The remaining input-contract question is therefore **VP-plugin version compatibility**, not whether Direct KG should alternatively consume arbitrary standalone `ontouml-schema` documents.

## Correction 2 — n-ary relations are not part of the current VP export scope

The VP plugin's internal `Relation` model can represent arbitrary arity, but the current `IAssociationTransformer` exports a Visual Paradigm association by transforming exactly its `from` and `to` ends into two relation-end properties.

Therefore n-ary relation transformation is NOT a required Direct KG decision for the currently defined VP-plugin-generated input. It can be added later if the VP export path begins generating n-ary relations.

## Correction 3 — generalization sets need more than simple class-partition handling

The plugin represents generalizations between classifiers, and relation classifiers must therefore be considered when defining relation generalization and any applicable generalization-set behavior.

Class covering/disjointness and property covering/disjointness cannot automatically be treated identically in OWL.

## Correction 4 — property stereotypes were missing

The current VP plugin supports:

```text
«begin»
«end»
```

as property stereotypes. Their Direct KG behavior remains undefined.

## Correction 5 — `categorizer` was missing

The current VP plugin serializes an optional generalization-set `categorizer`. This is semantically coupled to `«type»`, `«instantiation»`, and higher-order representation.

## Correction 6 — property flags were incomplete

The source contains:

```text
isOrdered
isReadOnly
```

and their Direct KG policy remains undefined.

## Correction 7 — VP-plugin-specific `isExtensional` remains relevant

The current VP plugin serializes `isExtensional`, so Direct KG needs an explicit treatment for it as long as VP-plugin-generated JSON is the source.

## Correction 8 — ontology identity was missing

The existing `--base-iri` rule defines the namespace for generated entities, but not necessarily the generated ontology's own IRI/version metadata.

## Correction 9 — standalone-schema-only fields must not be treated as current Direct KG inputs

Items such as standalone-schema `Project.namespace`, `customProperties`, additional metadata fields, and note/anchor structures must not be added to the current Direct KG handoff merely because they exist in the separate schema. They are outside the stated VP-plugin-generated input scope unless that scope is deliberately expanded later.
