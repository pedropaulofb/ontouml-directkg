# OntoUML DirectKG — Remaining Decisions Handoff

## 1. Purpose of this document

This document captures only the OntoUML DirectKG transformation-specification work that remains unresolved. It is intended to let a future Architect conversation continue making decisions and a future Documenter conversation update the normative specification without reconstructing earlier discussions.

It is not a history, a complete specification, or an invitation to reopen established decisions. Context from settled rules is included only when it constrains an open issue.

## 2. Current specification context

The following are established constraints, not open questions:

- DirectKG produces a simplified, domain-oriented RDF/OWL knowledge graph from JSON generated by `ontouml-vp-plugin`. The standalone `ontouml-schema` is a reference, not an additional input contract.
- Domain classes, class generalizations, supported primitive datatypes, custom datatype reification, attribute property kind, resolvable domains/ranges, explicit attribute multiplicities, property identity, IRI normalization/escaping, and the existing name-based collision framework already have accepted rules.
- Ordinary eligible binary class-to-class relations generate direct `owl:ObjectProperty` resources with the source classifier as `rdfs:domain` and the target classifier as `rdfs:range`.
- Inverse-property generation is settled. The modes are `all`, `informed`, `named`, and `none`, with `all` as the default. Eligibility, intentional omission, self-relations, material relations whose primary transformation succeeds, domain/range reversal, naming, labels, and collision handling have accepted rules.
- A generated inverse prefers the inverse-facing association-end role name. Where the established mode permits an unnamed inverse, its structural name is `inverseOf<ResolvedPrimaryPropertyLocalName>`. Generated auxiliary resources must not change the IRIs of source-backed resources.
- Every generated inverse has exactly one explicit assertion from inverse to direct property:

  ```turtle
  :inverseProperty owl:inverseOf :directProperty .
  ```

  The redundant reciprocal assertion is not emitted.
- Under `--iri-strategy id`, the direct property uses the target association-end ID and the inverse uses the source association-end ID. The association ID is not the direct-property IRI basis. Existing reversible ID escaping and exceptional-collision principles still apply.
- A binary relation with a missing or unresolved endpoint cannot generate either its direct property or an inverse. The global severity and continuation policy for malformed input remains open.
- `«instantiation»` and `«derivation»` are not processed as ordinary inverse-generating binary relations. Their target semantics remain open below.
- Current VP-plugin export is binary. N-ary relation transformation is outside the current specification scope unless the accepted input contract later expands.

## 3. Remaining decisions

### 3.1 Source, failure, and output contracts

### RD-01 — Supported VP-plugin serialization versions

**Issue / decision needed:** Define which `ontouml-vp-plugin` serialization versions and historical dialects DirectKG accepts.

**Context:** Current plugin output and older catalog `ontology.json` files differ in field shape and content. The new ID-based relation-property rule also depends on stable association-end IDs and an unambiguous source/target ordering.

**Existing constraints:**

- VP-plugin-generated JSON is the source contract.
- Supporting arbitrary standalone-schema documents is not implicitly in scope.
- For every supported binary-relation dialect, DirectKG must be able to identify the source end, target end, their IDs, and their referenced classifiers.

**Questions still open:**

- Is only one current plugin version supported, or are selected legacy dialects supported?
- If multiple dialects are supported, how are they detected?
- Does a compatibility layer normalize legacy fields before semantic transformation?
- Are unknown fields ignored, warned about, or rejected?
- What happens when a dialect cannot preserve the association-end identity/orientation required by the established direct/inverse IRI rules?

**Dependencies:** RD-02 and RD-04 require the supported-input boundary to be known.

### RD-02 — Malformed, incomplete, and dangling source data

**Issue / decision needed:** Define the global transformation policy for structurally unusable source constructs.

**Relevant cases:**

- missing, blank, duplicated, or invalid element IDs;
- null or dangling relation-end `propertyType` references;
- generalizations whose classifiers are absent;
- generalization sets referencing missing generalizations;
- derivations with unresolved endpoints;
- inconsistent relation semantics and diagram topology;
- malformed or unsupported multiplicity expressions.

**Established constraints:**

- DirectKG must not guess missing semantic targets.
- A relation with an unresolved endpoint produces neither its direct property nor an inverse.
- Diagram connectivity is not an established repair source.
- Distinct source resources must never be silently merged because of an IRI collision.

**Questions still open:**

- Does any structural-integrity failure abort the whole transformation?
- May DirectKG skip only the affected construct and continue with diagnostics?
- Which conditions are errors, warnings, or informational messages?
- Can partial output be considered successful, and how is that status reported?
- Should there be strict and permissive validation modes?

**Supporting evidence, not a normative rule:** The inspected OntoUML model corpus contains relations whose end IDs exist but whose `propertyType` references are null. This demonstrates that incomplete endpoints are a real compatibility case, but it does not establish the required failure policy.

### RD-03 — Unknown or non-standard stereotypes

**Issue / decision needed:** Define behavior for syntactically accepted but unrecognized class, relation, and property stereotypes.

**Credible alternatives already identified:**

- preserve any structurally safe baseline transformation, emit a warning, and invent no stereotype semantics;
- reject the affected construct or the complete input.

The first behavior has been discussed as compatible with DirectKG's pragmatic approach, but it has not been adopted.

**Dependencies:** The diagnostic severity and continuation behavior should align with RD-02. Additional semantic behavior must not be inferred merely from an unfamiliar stereotype name.

### RD-04 — Output serialization, OWL profile, determinism, and diagnostic delivery

**Issue / decision needed:** Define the externally supported output contract.

**Questions still open:**

- What is the default RDF syntax, and which additional serializations are supported?
- Which prefixes are emitted by default?
- Is the output guaranteed to remain in OWL 2 DL?
- How do optional punning, metamodeling, reification, property chains, or rules affect the declared profile?
- Is statement ordering deterministic where the syntax exposes ordering?
- Are diagnostics written to stderr, a log, a structured report, or more than one destination?
- How are partial-success and failure states represented?

**Existing constraint:** Turtle examples are illustrative and do not yet establish Turtle as the normative default.

### RD-05 — Ontology identity and header metadata

**Issue / decision needed:** Define the generated ontology resource and distinguish it from the namespace used for generated entities.

**Questions still open:**

- Is an `owl:Ontology` declaration always generated?
- How is its IRI derived from `--base-iri`, especially when the entity namespace ends in `#` or `/`?
- Are version IRIs, imports, titles, descriptions, creators, provenance, licenses, or source-project metadata emitted?
- Which metadata belongs in the ontology header rather than on individual generated resources?

**Existing constraint:** DirectKG must not accidentally import gUFO merely because gUFO informed some semantic analysis.

### 3.2 Enumeration semantics

### RD-09 — `«enumeration»` classes and literals

**Issue / decision needed:** Define how enumeration classes and their literals are represented.

**Credible alternative families:**

- reified OWL class plus `owl:oneOf`, with literals represented as individuals;
- OWL datatype/data range, potentially using `DataOneOf`.

**Why it matters:** The choice determines whether properties typed by an enumeration become object or datatype properties and affects literal identity, generalization, labels, and IRI generation.

**Questions still open:**

- How are literal IRIs or lexical values generated?
- Are literals source-identity-based or lexical-identity-based?
- How are language tags and literal datatypes handled?
- What happens with empty enumerations or duplicate names?
- How do enumeration classes participate in generalization?

**Existing constraint:** Participation of `enumeration` in established class-disjointness rules does not settle its value representation.

### 3.3 Relation, hierarchy, and higher-order semantics

### RD-11 — Relation-end multiplicities and OWL cardinality restrictions

**Issue / decision needed:** Define the complete mapping from binary-relation end multiplicities to OWL restrictions.

**Established constraints from later inverse decisions:**

- The direct property runs from source classifier to target classifier.
- A named inverse, when generated, runs from target to source and has an explicit `owl:inverseOf` assertion.
- Under the ID strategy, the direct and inverse properties use the target-end and source-end IDs respectively.
- The selected inverse-generation mode must not be silently overridden merely to express cardinalities.

**Questions still open:**

- Which end's multiplicity constrains instances of the source class, and which constrains instances of the target class?
- How do lower, upper, exact, and finite-range multiplicities map to OWL?
- Are restrictions qualified or unqualified?
- When a named inverse exists, should the source-end constraint be expressed through that inverse?
- When inverse mode produces no named inverse, should DirectKG use an anonymous `ObjectInverseOf(...)` expression, omit the source-side restriction with diagnostics, or use another defined representation?
- What do `null`, `*`, and non-numeric/theoretical expressions such as `a..b` mean?

**Edge cases:** self-relations, malformed multiplicities, unresolved endpoints, material relations, and a change of inverse-generation mode.

### RD-12 — Generalization between relations

**Issue / decision needed:** Decide whether a relation-to-relation generalization becomes `rdfs:subPropertyOf` and define its directional consequences.

**Questions still open:**

- Is direct-property subproperty mapping adopted?
- What compatibility checks are required between generated property kinds, domains, and ranges?
- If both relations have generated named inverses, should corresponding inverse subproperty axioms be emitted explicitly, or is entailment through `owl:inverseOf` sufficient?
- What happens when only one or neither inverse is generated under the selected mode?
- Does relation generalization imply subsetting semantics for corresponding association ends?
- Which diagnostics apply to incompatible mappings?

**Dependencies:** Resolve with RD-14 and before relation generalization sets in RD-13.

### RD-13 — Generalization sets

**Issue / decision needed:** Define separate mappings for class and relation generalization sets.

**Class-set questions:**

- How are `isDisjoint` and `isComplete` represented?
- When is `owl:disjointUnionOf` appropriate?
- When should `owl:AllDisjointClasses`, pairwise disjointness, or union-based covering be used?

**Relation-set questions:**

- Can disjoint relation specializations use `owl:AllDisjointProperties`?
- What support or limitation is declared for complete relation sets, given the absence of an ordinary OWL property-union constructor?
- How do generated inverses participate, if at all?

**Higher-order dependency:** The optional `categorizer` must be resolved consistently with RD-15.

### RD-14 — Property subsetting and redefinition

**Issue / decision needed:** Define target behavior for `subsettedProperties` and `redefinedProperties`.

**Subsetting questions:**

- Does explicit subsetting become `rdfs:subPropertyOf`?
- How does explicit end subsetting relate to relation generalization?
- Because direct and inverse properties now correspond to target and source association ends respectively, which generated direction does each referenced end constrain?
- What happens when a referenced source end corresponds to an inverse that is not generated under the selected mode?

**Redefinition questions:**

- Can redefinition be represented faithfully in OWL?
- Is any part equivalent to subproperty semantics?
- Must changed ranges or cardinalities be represented separately?
- Should unsupported redefinition be ignored, annotated, or diagnosed?

**Dependencies:** RD-11 and RD-12 should be settled first or jointly.

### RD-15 — `«type»`, `«instantiation»`, higher-order modeling, and categorization

**Issue / decision needed:** Select one coherent higher-order representation.

**Topics that must be decided together:**

- whether an OntoUML `«type»` is only an `owl:Class`, uses OWL 2 punning, uses separate class/individual IRIs, or uses another metamodeling pattern;
- whether `«instantiation»` becomes `rdf:type`, an object property, an annotation, a metamodeling construct, or a combination;
- whether and how class `order` values (`1`, `2`, ..., `*`) affect generated OWL;
- whether `isPowertype` receives a DirectKG representation;
- how a generalization-set `categorizer` relates to its specific classes.

**Established constraints:**

- `«instantiation»` is not an ordinary inverse-generating relation.
- Names such as `classifiedBy`, `classifies`, `instanceOf`, and `hasInstance` must not be introduced before the representation is decided.
- Any selected pattern must be reflected in the OWL-profile decision in RD-04.

### RD-16 — Transformation of `«derivation»` and non-class relation endpoints

**Issue / decision needed:** Decide whether and how an explicit derivation relation appears in the output.

**Context:** DirectKG already uses `«derivation»` internally to locate the grounding relator used to name an unnamed material relation. That transformation-time use does not define a target representation for the derivation itself. A derivation can connect a relation classifier to a class, while ordinary DirectKG relations become OWL properties.

**Credible alternatives already identified:**

- omit the derivation after transformation-time use;
- preserve it as annotation;
- use punning/metamodeling;
- reify the relevant source relation;
- adopt another explicitly justified mechanism.

**Dependencies:** This should be resolved with or after RD-15 and must respect RD-04. It should also establish the policy for any other supported relation endpoint that is not an ordinary class.

### RD-17 — Additional OWL semantics from relation stereotypes

**Issue / decision needed:** Determine whether recognized relation stereotypes generate semantics beyond their already-established naming behavior.

**Questions still open:**

- Do any parthood relations generate transitivity, asymmetry, irreflexivity, or other characteristics?
- Do characterization, mediation, dependence, or event relations generate generic superproperties, property chains, or other axioms?
- Do any stereotypes imply functionality or inverse functionality?
- What, if any, is the generic semantic treatment of `comparative` beyond ordinary relation transformation?
- For `material`, is any relator-derived property-chain or SWRL-style derivation emitted, or is the relator used only for naming/diagnostics?

**Established constraints:**

- Stereotype-derived direct and inverse names are already settled and must not be reopened here.
- Every generated inverse already receives `owl:inverseOf`; that assertion is not an additional stereotype-specific question.
- No property characteristic may be inferred merely because it sounds intuitively plausible.

The historical 2013 SWRL-style material-relation behavior has been discussed as a reference but has neither been adopted nor rejected for DirectKG.

### RD-18 — Property stereotypes `«begin»` and `«end»`

**Issue / decision needed:** Define the treatment of the property stereotypes `begin` and `end`.

**Questions still open:**

- Which source properties may validly carry them?
- Do they affect property naming?
- Do they imply event-boundary or temporal semantics representable in OWL?
- Are they preserved as annotations, ignored, or diagnosed when no direct semantic mapping is adopted?

They are property stereotypes, not relation stereotypes, and must not inherit relation-stereotype behavior automatically.

### 3.4 Classifier and property metaproperties

### RD-19 — `«abstract»` stereotype and `isAbstract`

**Issue / decision needed:** Define target behavior for two distinct source concepts:

- the class stereotype `«abstract»`;
- the classifier flag `isAbstract = true`, which can also apply to relations.

**Context:** `«abstract»` already participates in an established broad disjointness group. That does not settle additional stereotype semantics. OWL has no direct construct expressing that a classifier cannot have direct instances or assertions except through a specialization.

**Questions still open:** Should either concept be ignored, annotated, diagnosed, or represented through a justified metamodeling construct? They must not be conflated.

### RD-20 — `isDerived`

**Issue / decision needed:** Decide whether `isDerived` on classifiers and properties is ignored, annotated, used diagnostically, or given target semantics.

**Constraint:** `isDerived = true` is distinct from an explicit `«derivation»` relation and must not inherit RD-16 behavior automatically.

### RD-21 — `isExtensional`

**Issue / decision needed:** Decide whether `isExtensional` generates an OWL axiom, is preserved as annotation, is ignored, or is recognized only for input compatibility.

**Dependency:** Confirm its shape and availability for each supported VP-plugin dialect in RD-01 before fixing semantic behavior.

### RD-22 — `restrictedTo`

**Issue / decision needed:** Define whether `restrictedTo` is used only internally, generates OWL axioms, is preserved as annotation, or affects validation and disjointness beyond the current stereotype-based rules.

**Relevant edge case:** A class's effective `restrictedTo` set may be broader than the usual default associated with its stereotype and may include `type`, creating a dependency on RD-15.

### RD-23 — `isOrdered`

**Issue / decision needed:** Decide how ordered property values are treated, given that ordinary OWL properties do not directly encode UML-style ordering.

**Credible alternatives:** ignore the flag, preserve it as annotation, warn when true, or adopt a list/sequence reification pattern.

A lightweight annotation/diagnostic policy was discussed as pragmatically preferable to structural reification, but it was not adopted.

### RD-24 — `isReadOnly` and existential dependence

**Issue / decision needed:** Define separate policies for relation ends and class attributes.

**Relation-end questions:**

- Does the VP-plugin's opposite-end `isReadOnly` encoding of existential dependence generate any OWL axiom?
- Is that meaning already captured by a relation stereotype in some cases?
- What happens when `isReadOnly = true` occurs without a corresponding stereotype?
- Is the flag preserved as annotation in addition to any semantic mapping?

**Attribute questions:** Is attribute `isReadOnly` ignored, annotated, diagnosed, or otherwise represented?

Any semantic mapping must be justified from OntoUML/UFO semantics rather than inferred solely from UML mutability.

### RD-25 — `aggregationKind` beyond established orientation/naming use

**Issue / decision needed:** Decide whether `COMPOSITE`, `SHARED`, and `NONE` are used only during transformation, preserved as annotations, or generate additional constraints/property characteristics.

**Established constraint:** Existing use of `aggregationKind` to identify the whole end of relevant mereological relations is not open. No standard OWL characteristic should be inferred from UML aggregation without explicit semantic justification.

### 3.5 Naming, metadata, provenance, and structural scope

### RD-26 — Labels for unnamed generated resources

**Issue / decision needed:** Complete the label policy without reopening settled inverse labels.

**Established decisions:**

- An unnamed class with a synthetic IRI receives no invented `rdfs:label`.
- A named direct property preserves its source name as `rdfs:label`.
- A generated inverse with an inverse-facing role preserves that role as its label.
- An unnamed inverse using the `inverseOf...` structural fallback receives no synthetic label.

**Questions still open:**

- Does an unnamed direct relation whose IRI comes from a target role, stereotype mapping, grounding relator, or synthesized source-target name receive a generated label?
- If so, how is that label marked as generated rather than source-provided?

**Trade-off:** Strict source fidelity favors no label when the source name is absent; usability favors labels derived from meaningful generated local names.

### RD-27 — Multilingual selection and general annotation policy

**Issue / decision needed:** Define deterministic handling of multilingual `name` and `description` values and other supported source metadata.

**Questions still open:**

- Which language variant supplies a name-based IRI when several names exist?
- Is there a configured language/preference order, and what is the deterministic fallback?
- Must the same selection apply to classes, attributes, direct relations, association-end roles, material-relator names, and synthesized names?
- Are all source-language variants emitted as language-tagged `rdfs:label` values?
- Does `description` become `rdfs:comment` or another annotation?
- Which supported project metadata is propagated?
- Must explicit source language tags always be preserved, and are absent tags left absent?

**Dependency:** The metadata actually available depends on RD-01. Ontology-level placement also depends on RD-05.

### RD-28 — Source-ID provenance in name-based output

**Issue / decision needed:** Decide whether resources generated under `--iri-strategy name` carry annotations linking them back to source IDs.

**Why it matters:** Name-based IRIs can change when modelers rename elements; source identifiers support traceability, debugging, and result comparison.

**New consequence of the established end-based ID rule:** If provenance is emitted, the specification must decide whether a direct relation property records:

- the target association-end ID that identifies it under ID mode;
- the enclosing association ID;
- or both.

For a generated inverse, the corresponding source-end ID is the directional identity, while the enclosing association may still be useful provenance.

**Questions still open:** Select the annotation vocabulary, cardinality, lexical form, and treatment of multiple relevant source IDs. Candidates such as a DirectKG annotation or `dct:identifier` were discussed but not selected.

### RD-30 — `propertyAssignments`

**Issue / decision needed:** Define whether custom tagged values serialized through `propertyAssignments` are ignored, annotated, diagnosed, mapped through a whitelist, or exposed to user-defined mappings.

**Constraint:** Arbitrary tagged values must not be converted blindly into OWL properties without an explicit namespace, datatype, and semantic policy.

### RD-31 — Package semantics and namespaces

**Issue / decision needed:** Decide whether source packages are ignored, retained only as provenance, represented as modules/ontologies, preserved as annotations, or allowed to influence generated IRIs.

**Constraint:** Package paths must not silently become parts of IRIs, because package refactoring would then change resource identity. Any module/ontology mapping must align with RD-05.

### RD-32 — Diagrams, element views, and layout geometry

**Issue / decision needed:** Establish an explicit scope rule for diagrams and concrete-syntax data.

**Questions still open:** Are diagrams/views ignored silently, preserved separately as provenance, or partially annotated? Can visual topology ever be used diagnostically when semantic references are broken?

**Established constraint:** Layout, paths, coordinates, and view placement must not change the ontology generated from valid underlying model elements. Diagram data is not currently an authorized source for repairing unresolved relation endpoints.

## 4. Dependencies and recommended discussion order

The following order minimizes reopening and cross-topic revision:

1. **Source and failure contract:** RD-01, RD-02, RD-03.
2. **Higher-order foundation:** RD-15 and RD-16, because they may affect OWL profile, relation endpoints, categorization, and ontology structure.
3. **Relation cardinality:** RD-11.
4. **Relation hierarchy:** RD-12, RD-14, then the relation aspects of RD-13.
5. **Class/value constructs:** The class aspects of RD-13, then RD-09.
6. **Stereotype and metaproperty semantics:** RD-17 through RD-25.
7. **Labels, language, provenance, and tagged values:** RD-26, RD-27, RD-28, and RD-30.
8. **Packages and ontology identity:** RD-31 and RD-05.
9. **Concrete syntax and final output contract:** RD-32 and RD-04, revisiting the OWL-profile portion of RD-04 after all semantic constructs are known.

Some topics can be discussed in parallel, but the following dependencies should be preserved:

- RD-11 constrains RD-12 and RD-14.
- RD-12 and RD-14 constrain relation generalization sets in RD-13.
- RD-15 constrains `categorizer`, `order`, `isPowertype`, RD-16, RD-19, RD-22, and the OWL profile.
- RD-01 constrains any policy for source fields whose availability differs across plugin versions.
- RD-02, RD-03, and RD-04 must ultimately define one coherent diagnostic and exit-status contract.
- RD-27, RD-28, RD-31, and RD-05 collectively determine ontology metadata and provenance placement.

## 5. Handoff notes

- Only explicit user acceptances and formalized decisions are normative. Recommendations identified above remain open.
- Any older specification text saying that inverse-property policy is open is superseded. Inverse modes, eligibility, naming, labels, collision handling, self-relations, material-relation handling, domain/range reversal, `owl:inverseOf`, and ID-based directional identity are established.
- Any older text saying that an ID-based direct relation property uses the association/`Relation` ID is superseded. It uses the target association-end ID; a generated inverse uses the source association-end ID.
- Relation-end multiplicity remains open despite the completed inverse policy. Do not infer cardinality behavior merely from the directional IRI mapping.
- The 2013 OntoUML-to-OWL/SWRL transformation is historical input, not automatically accepted DirectKG behavior.
- The standalone OntoUML schema and catalog models are supporting references, not substitutes for the VP-plugin source contract.
- N-ary relations, standalone-schema-only fields, and ordinary implementation architecture are outside the present unresolved specification scope unless a later scope decision explicitly brings them in.
